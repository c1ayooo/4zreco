# 部署手册（Linux 测试机 / 生产机通用）

本文记录**实测可用**的部署流程与踩过的坑。路径按测试机 `/opt/4zreco` 写，
生产机同构，换路径即可。

## 0a. 内网机安装：LAN 本地源配方（Kali 2026-10 实测，两次全流程）

直连 GitHub 下载大文件在内网测试机（Kali VM 等）上必然卡死。配方：**Windows 当源，Kali 拉本地**。

```bash
# ── Windows 侧（Git Bash）──
mkdir -p /c/Users/<you>/AppData/Local/Temp/r419 && cd /c/Users/<you>/AppData/Local/Temp/r419
gh release download v0.4.19 --repo c1ayooo/4zreco --pattern "4zreco-0.4.19-linux-amd64.zip" --pattern "install.sh" --pattern "SHA256SUMS" --clobber
# 本地比对 SHA256（与 SHA256SUMS 里的 linux-amd64 行一致才继续）
sha256sum 4zreco-0.4.19-linux-amd64.zip

# 给 install.sh 打本地源补丁（⚠️ $REPO 是变量，sed/replace 后必须确认替换处数）
python - <<'PY'
import io
s = io.open("install.sh", encoding="utf-8").read()
old = 'https://github.com/$REPO/releases/download'
assert old in s, "anchor missing"
s = s.replace(old, 'http://<windows-lan-ip>:8124/v0.4.19')   # 记得拼版本路径
io.open("install.sh", "w", encoding="utf-8").write(s)
PY

# ⚠️ 双层目录坑：原 URL 是 .../download/$VERSION/$zip，补丁把前半段换掉后 $VERSION
# 还会再展开一层 → 实际请求 <root>/v0.4.19/v0.4.19/<zip>。本地源必须建双层同名目录：
mkdir -p v0.4.19/v0.4.19 && cp 4zreco-0.4.19-linux-amd64.zip SHA256SUMS v0.4.19/v0.4.19/

# 起源（端口被旧会话残留占用时：netstat -ano | grep 8124 按 PID 全杀再起）
python -m http.server 8124 --bind 0.0.0.0 &
# 自检（三个都要 200）：zip / install.sh / v0.4.19/v0.4.19/zip

# ── Kali 侧 ──
curl -sS -O http://<windows-lan-ip>:8124/install.sh && chmod +x install.sh
sudo ./install.sh --mode=binary
# Windows 侧 LAN IP 看 `ipconfig`（VMware NAT 网段一般是 x.x.x.1）
```

坑位清单：① install.sh 替换锚点必须断言存在（历史上有静默空转先例）；② 双层 $VERSION 目录；
③ 8124 跨会话残留进程；④ Windows 侧 curl 自检 200 ≠ Kali 侧可达——Kali 本机也要 curl 一遍；
⑤ 装完 `curl 127.0.0.1:8787/api/health` + `/api/version` 双验。

## 0. 前置

- 二进制来自 GitHub Release（CI 构建，7 个 asset）：
  `4zreco-<版本>-linux-amd64.zip` + `SHA256SUMS`。
- **必须校验 SHA256**，官方 `SHA256SUMS` 里对应行必须 OK 才部署。
- 下载走 GitHub API 的 asset URL（`Accept: application/octet-stream`），
  或 `browser_download_url` 跟随 302。**asset 名字不带 `v` 前缀**：
  tag 是 `v0.4.19`，asset 是 `4zreco-0.4.19-linux-amd64.zip`。

```bash
sha256sum 4zreco-0.4.19-linux-amd64.zip
grep 'linux-amd64' SHA256SUMS | sed 's/  */  /' | sha256sum -c -
# → 4zreco-0.4.19-linux-amd64.zip: OK
```

## 0b. 从旧名版本（ARTEX ≤ v0.4.18）升级到 4zreco

v0.4.19 起发行资产改名 `4zreco-<版本>-<os>-<arch>.zip`（旧版为 `artex-...`）。
**旧版本内置的更新器找的是旧资产名，无法一键更新到 v0.4.19+**，需要先用新安装包
重装一次（幂等：保留 `config.json` / `jwt.key` / `data/` / 数据库，只换程序）：

```bash
curl -fsSL https://raw.githubusercontent.com/c1ayooo/4zreco/main/install.sh -o install.sh
sudo bash install.sh --mode=binary --version=v0.4.19
```

装完确认只剩新服务在跑（旧机若还有 `artex.service` 要停掉，避免双实例争同一数据库）：

```bash
systemctl disable --now artex 2>/dev/null || true
systemctl status 4zreco --no-pager
```

升级到 v0.4.19 之后，后续版本可继续用页面「一键更新」。若下载失败：先确认
`settings.install_proxy` 指向的代理可用（只影响下载；GitHub API 检查可直连），
不可用就清空或换成可用代理再试。

## 2. 停服务 → 换二进制 → 启服务

### ⚠️ 任务运行期间部署 = 掐断在跑的意图

`systemctl stop artex` 会取消所有在跑的 worker run，它们被落成
`blocked: context canceled`，**内容全部丢掉**（已写回的事实还在，但那一步
的探测没了）。实测 2026-10-21 连续部署两版，任务 4 的 8 个意图全被掐断。

**部署前先看有没有任务在跑**：

```bash
sudo -n -u postgres psql -d artex -tA -F'|' -c \
  "SELECT id, status, left(name,30) FROM tasks WHERE status NOT IN ('done','failed','timeout');"
```

有在跑的任务时，两个选择：

- **等它跑完**（推荐，改动不急时）
- **先优雅暂停**（让 worker 写回成果再停）：
  ```bash
  curl -s -X POST "$API/api/tasks/<id>/control" -H "Authorization: Bearer $TOKEN" \
       -H 'Content-Type: application/json' -d '{"paused":true}'
  ```
  等它进 paused 再 stop。

**万一已经掐断了**，用官方接口把 blocked 意图恢复成 open（worker 会重新领取）：

```bash
curl -s -X POST "$API/api/tasks/<id>/intents/rerun-blocked" \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{}'
# → {"id":"4","queued":false,"reopened":8}
```

### 实际替换步骤

```bash
sudo -n systemctl stop 4zreco

SRC=/tmp/4zreco-upload/unpack/4zreco-<版本>-linux-amd64
D=/opt/4zreco

# 二进制：先写 .new 再 mv -f，避免 ETXTBSY（正在运行的二进制写不进去）
sudo -n cp "$SRC/4zreco" "$D/.4zreco.new"
sudo -n chmod +x "$D/.4zreco.new"
sudo -n mv -f "$D/.4zreco.new" "$D/4zreco"

sudo -n cp "$SRC/4zreco-hostd" /usr/local/bin/.4zreco-hostd.new
sudo -n chmod +x /usr/local/bin/.4zreco-hostd.new
sudo -n mv -f /usr/local/bin/.4zreco-hostd.new /usr/local/bin/4zreco-hostd

# 维护工具（v0.4.13+ 随包分发）：
sudo -n install -m 0755 "$SRC/4zreco-maint" "$D/4zreco-maint"

# ★ skills 必须用「合并」写法：cp -r "$SRC"/skills/. "$D"/skills/
#   写成 cp -r "$SRC"/skills "$D"/ 时，目标 skills 已存在，GNU cp 的行为
#   不保证把每个子 skill 补齐——实测漏掉过 api-recon，而 DB 里三个 agent
#   都绑定了它，结果 worker/auto/pentest 静默拿不到这个能力。
sudo -n mkdir -p "$D/skills"
sudo -n cp -r "$SRC"/skills/. "$D"/skills/

sudo -n cp "$SRC/start.sh" "$D/start.sh"
sudo -n chmod +x "$D/start.sh"
echo "<版本>" | sudo -n tee "$D/.version" >/dev/null
sudo -n chown -R 4zreco:4zreco "$D"

sudo -n systemctl start artex
sleep 7
sudo -n journalctl -u artex --since '30 seconds ago' --no-pager | grep -Ei 'listening|panic'
```

**部署后必查**：

```bash
sudo -n ls /opt/4zreco/skills/          # skill 数量应与 release 里一致
sudo -n cat /opt/4zreco/.version
```

## 3. 已知的环境事实

- **服务进程带着 `HTTP_PROXY` / `HTTPS_PROXY`**（systemd `Environment=`）。
  Go 里 `http.DefaultTransport.Clone()` 会继承这个代理——想「直连」必须
  **显式 `transport.Proxy = nil`**。本项目已有三处按这个约定写：
  `agent/provider.go`（LLM）、`traffic/traffic.go`（目标流量）、
  `server/proxypool_api.go`。
- **出网代理 `10.10.70.14:7897` 对部分站点不通**（实测 cisa.gov /
  services.nvd.nist.gov 会「CONNECT 200 后 TLS 握手 EOF」，而 github 正常）。
  直连这两个源是通的。
- 测试机到 GitHub 间歇性失败；本机 GitHub 需走 Clash 代理
  （`socks5h://127.0.0.1:7897`）。

## 4. 登录凭据

- 用户名固定 `ARTEX`；密码是 bcrypt hash，存在 `settings` 的
  `auth.password_hash`。
- **重置密码**：删掉那一行 → `POST /api/auth/init`（body `{"password":"..."}`）
  → 返回 token。`init` 用 `InsertSettingIfAbsent` 保证只能设一次。
- 改密码用 `POST /api/auth/change-password`（需要**旧密码** + 有效 token）。

## 7. 拦截规则自检（2026-10-22 整改后）

拦截规则在 **v0.3.78** 重新划过分层：内置规则不再是「一律 deny」，而是分成
**明令禁止**（直接拒绝，不调模型）/ **交给 Agent 研判**（模型裁决）/ **人工确认**
（转审批）。全新安装的库里应当是这个状态。

```bash
TOK=$(curl -s -X POST http://127.0.0.1:8787/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"ARTEX","password":"<密码>"}' | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

# 规则总数与三种动作的分布
curl -s http://127.0.0.1:8787/api/intercept/rules -H "Authorization: Bearer $TOK" \
  | python3 -c "
import json,sys
rs=json.load(sys.stdin)['rules']
from collections import Counter
c=Counter(r['action'] for r in rs if r['name'].startswith('[内置]'))
print('内置规则总数:', sum(c.values()))
print('动作分布:', dict(c))
for r in sorted(rs, key=lambda x: -x['priority']):
    if r['name'].startswith('[内置]'):
        print(f\"  {r['action']:>5} | {r['name']}\")
"
```

**期望值**（全新安装）：

| 动作 | 条数 | 含义 |
|---|---|---|
| `deny` | 10 | 明令禁止：任何语境都不可逆且无合法渗透用途 |
| `judge` | 12 | 交给 Agent 研判：作用对象取决于上下文 |
| `ask` | 0 | 人工确认（v0.3.86 起：listener 启停规则已移除，目标工具从未实现；已部署实例残留的该条规则无害，可手动删） |

**逐条核对要点**

- 每条规则的 `timeout_enabled` 应为 `true`，且 `timeout_seconds` / `timeout_action`
  是**该规则自己的值**（研判类 90s/allow，硬禁类 30s/deny）。这在 v0.3.78 之前
  是死字段——界面显示 60s/deny，实际生效的是全局 180s/ask。
- 「数据外泄管道」规则应当**已启用**（`enabled=true`）。它此前默认停用，因为
  旧 pattern 会误伤 `curl 目标 | nc 自己的回连器` 这种正常回连；新 pattern
  只拦「@文件上传」。
- 「SQL DROP DATABASE / SCHEMA」与「SQL DROP TABLE / INDEX / VIEW」应当是
  **两条独立的规则**（旧版本是一条合并的 DROP 规则）。

**运行期行为验证**（需要配好 LLM profile，否则研判类规则会走失败策略）：

发一条会触发规则的任务，然后在「系统 → 拦截审批 → 历史」里看记录：

- 触发**明令禁止**的命令（如 `mkfs.ext4 /dev/sda`）→ 记录里 `decision_source`
  是 `rule`，理由是规则自带的 message，**没有 `[模型]` 前缀**（说明没调模型）。
- 触发**研判**的命令（如 `rm -rf /var/www/html`）→ 理由带 **`[模型]` 前缀**
  （说明走了模型裁决），且 `rule_id` 指向命中的那条内置规则。

平台没有「试匹配」的接口（规则只在真实工具调用时生效），所以只能这样观察。

> ⚠️ **升级已有实例前先备份数据库**。规则迁移（`intercept_builtin_rule_actions_v1`）
> 会改写 `intercept_rules` 表的 action/timeout/pattern 字段。它只改「仍是内置
> 默认值」的行（按 action + timeout 三元组 + pattern 判定），**用户自己改过
> 的规则不动**——但备份仍然必须做。

## 9. v0.3.80 起的版本自检：skill 与中间件工具

v0.3.80 加了 `vuln-hunting` skill（主动漏洞挖掘方法论）与「中间件协议」工具
分类。装完后可以这样确认它们真的生效了。

### 9.1 skill 是否真的被模型看到

skill 的文件在 `<安装目录>/skills/`，**可见性绑定在 DB**。两者任一不对，
模型就看不到这个 skill——而页面的 skill 列表来自 DB，**看不出文件解析失败**。

```bash
# 1) 文件在不在
ls -la /opt/4zreco/skills/

# 2) frontmatter 能不能被解析（name + description 都要有值）
#    没有 description 的 skill 在模型面前等于不存在
for f in /opt/4zreco/skills/*/SKILL.md; do
  echo "=== $f"
  sed -n '1,5p' "$f"
done
```

**v0.3.80 之前有个坑**：`skills/scopesentry/SKILL.md` 的 frontmatter 结束符被
写成了 `## name:`（而不是 `---`），norma 找不到 frontmatter 边界 → 整块 YAML
没被解析 → 那个 skill 从来没在模型面前出现过。v0.3.80 已修。

### 9.2 中间件协议工具

页面「系统 → 宿主环境」里应多出「**中间件协议**」一组，15 个工具：

MQTT gmqtt / paho-mqtt；消息队列 pika / amqpstorm / confluent-kafka / kombu；
数据库 pymongo / pymysql / psycopg2-binary / redis；SOAP zeep；
GitLab python-gitlab；网络设备 netmiko / napalm；SIEM splunk-sdk。

**装的时候注意**：这些是**纯库**（没有命令行入口），平台用

纯库，会报 "No apps associated with package ..."）。装完后验证：

```bash
python3 -c "import gmqtt, pika, pymongo, zeep, netmiko; print('ok')"
```

### 9.3 近期高危快通道

漏洞情报同步现在有两条线：**主同步**（全量目录）与**快通道**（按发布时间拉
最近 7 天、只收 CVSS≥9.0 或 CISA KEV）。快通道的游标独立，间隔默认 30 分钟。

```bash
# 快通道的游标与入库量
sudo -u postgres psql -d artex -tAc "
SELECT source, total_synced, left(coalesce(cursor,''),30), coalesce(last_error,'')
  FROM vuln_sync_state"
```

看到 `nvd_fastlane` 这一行有 `total_synced` 增长即说明快通道在跑。
若看到 `nvd rate limited`，那是 NVD 限速——两条线共享额度，平台已用闸门协调，
若仍超限则配 `NVD_API_KEY`（限速从 5 次/30s 提到 50 次/30s）。

## 10. 排障：网页打不开但「服务状态正常」

**症状**：`systemctl status artex` 显示 `active (running)`，但网页打不开。

**这在 v0.3.81 之前是个真问题**（现在已修，但排查思路仍然适用）：

- systemd 看到的是 **`start.sh` 这个包装脚本**还活着（它正在等 artex 子进程），
  而真正崩的是 artex 本体。所以状态是 running，**实际全挂**。
- 典型触发：数据库密码与 `config.json` 不一致、schema 迁移失败、端口被占。
  这些都是**永久性**故障，崩溃在无限重试中，首因被日志淹没。

**v0.3.81 起**：start.sh 连续 5 次异常退出就放弃自拉起，systemd 的
StartLimit 也会让单元进入 `failed (start-limit-hit)`。所以现在**状态会如实
显示故障**。

**排查步骤**：

```bash
# 1) 看真实日志（别只看 status）
sudo journalctl -u artex --no-pager -n 50 | grep -vE "collation|警告|描述|提示"

# 2) 看崩溃计数与放弃自拉起的提示
sudo journalctl -u artex --no-pager | grep -E "异常退出|放弃自拉起" | tail -10

# 3) 数据库密码是否与 config.json 一致（★ 最常见的原因）
sudo -u postgres psql -tAc "select rolpassword is not null from pg_authid where rolname='artex'"
sudo python3 - <<'PY'
import json, subprocess
c = json.load(open('/opt/4zreco/config.json'))['database']
env = {'PGPASSWORD': c['password'], 'PGHOST': c.get('host','127.0.0.1'),
       'PGPORT': str(c.get('port',5432)), 'PGUSER': c['user'],
       'PGDATABASE': c['dbname']}
r = subprocess.run(['psql','-tAc','select 1'], env=env, capture_output=True, text=True)
print('rc=', r.returncode, 'err=', r.stderr.strip()[:120])
PY

# 4) 端口是否被占
ss -tlnp | grep -E ":8787|:8788"
```

**改密码的正确做法**（别只改角色不改 config.json，反之亦然）：

```bash
# 改角色密码 → 同步改 config.json（两者必须一致）
sudo -u postgres psql -c "ALTER ROLE artex LOGIN PASSWORD '<新密码>'"
sudo python3 - <<'PY'
import json
p='/opt/4zreco/config.json'
c=json.load(open(p)); c['database']['password']='<新密码>'
json.dump(c, open(p,'w'), indent=2)
PY
sudo chmod 600 /opt/4zreco/config.json
sudo systemctl restart 4zreco
```

> install.sh 在**角色已存在**时会用新生成的密码同步 `ALTER ROLE`（v0.3.79 起），
> 并把同一个密码写进 config.json——两者天然一致。

## 文档证据转图片预览（v0.4.21 起）

任务里抓到的 Word/Excel/PPT/PDF 会自动取样转成图片，在任务总览「证据附件」
与报告里直接查看（不再只有下载链接）。

- **依赖**：`libreoffice-writer libreoffice-calc libreoffice-impress`
  （Office→PDF）+ `poppler-utils`（`pdftoppm` PDF→JPEG）+ `imagemagick`
  （缩略图兜底）。`install.sh --with-tools` 默认装齐；Docker 镜像已内置；
  已有实例可在「系统 → 宿主环境」页补装 `libreoffice` / `poppler`。
- **取样规则**：每份文档最多 **前 3 页**，JPEG（长边 1600、质量 82）；PDF
  直接渲染，Office 先经 LibreOffice 转 PDF 再渲染。预览是 sidecar 文件：
  `data/tasks/<id>/artifacts/previews/<artifact_id>/page-N.jpg`，不占
  100 个附件限额，按任务 100MB 预览总量保护。
- **状态**：附件列表的 `preview_state` 为 `pending/ready/failed/skipped`，
  失败原因在 `preview_error`（缺依赖会提示装包）。前端可单条「重新生成」。
- **历史任务补预览**：

```bash
sudo -u 4zreco /opt/4zreco/4zreco-maint previews --config /opt/4zreco/config.json --task 5
# 或全部任务（--force 重新生成已 ready 的）
sudo -u 4zreco /opt/4zreco/4zreco-maint previews --config /opt/4zreco/config.json --all
```

- **排障**：`soffice --headless --convert-to pdf` 单次超时 120s；LibreOffice
  转换全局串行（避免 profile 锁冲突），大文档排队时看到 `pending` 属正常。

## 报告公文字体（v0.4.4 起，零配置）

导出 Word 报告为 GB/T 9704-2012 公文版式（仿宋_GB2312 正文三号 / 方正小标宋_GBK
文件标题二号 / 楷体_GB2312 二级标题 / 黑体一级标题，28 磅固定行距、首行缩进 2 字、
每面 22 行网格）。三个公文字体已通过 go:embed 打进二进制，并在导出时嵌入 .docx
（ECMA-376 odttf）——**接收方机器不装这些字体也能原样渲染**，服务器侧零配置。

注意两点：

1. 二进制体积因内嵌字体增大约 21MB（zip 压缩后 docx 增量约 10MB/份）。
2. 导出 PDF（可选）：服务器装 LibreOffice 后可离线转换——
   `soffice --headless --convert-to pdf 报告.docx`。Linux 机器若要 PDF 里字体
   正确，仍建议把字体装进系统（/usr/share/fonts/gongwen + fc-cache），因为
   LibreOffice 对 docx 嵌入字体的支持不完整：

   ```bash
   sudo mkdir -p /usr/share/fonts/gongwen
   # 从仓库 report/fonts/ 取（或用户提供的公文字体包），ASCII 文件名即可
   sudo cp report/fonts/*.ttf /usr/share/fonts/gongwen/
   sudo fc-cache -fv /usr/share/fonts/gongwen
   fc-list | grep -E "仿宋_GB2312|楷体_GB2312|方正小标宋"
   ```

## 数据盘扩容与迁移（2026-11-02 Kali 实测）

根盘紧张时把 `data/` 迁到独立盘（以下以新盘 `/dev/sdb` 100G 为例，停机约 2–3 分钟）：

```bash
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT            # 确认新盘无分区、无挂载
sudo parted -s /dev/sdb mklabel gpt mkpart primary ext4 0% 100%
sudo mkfs.ext4 -L <name>-data /dev/sdb1
sudo systemctl stop artex
sudo mkdir -p /mnt/newdata && sudo mount /dev/sdb1 /mnt/newdata
sudo rsync -aHAX /opt/4zreco/data/ /mnt/newdata/
sudo mv /opt/4zreco/data /opt/4zreco/data.old && sudo mkdir -p /opt/4zreco/data
sudo umount /mnt/newdata && sudo mount /dev/sdb1 /opt/4zreco/data
sudo chown artex:artex /opt/4zreco/data
UUID=$(sudo blkid -s UUID -o value /dev/sdb1)
echo "UUID=$UUID /opt/4zreco/data ext4 defaults,nofail 0 2" | sudo tee -a /etc/fstab
sudo systemctl start artex && df -h /opt/4zreco/data
# 验证文件数与迁移前一致后再删备份：sudo rm -rf /opt/4zreco/data.old
```

`nofail` 必须加：盘异常时不能把系统拖进紧急模式。

## 附件 403 / 图片打不开（v0.4.18 起）

附件文件必须对服务运行用户（默认 `artex`）可读。历史上 `4zreco-maint`
以 root 补登记时写过 0600 属 root 的文件，`http.ServeFile` 会直接返回 403。
修复：

```bash
sudo /opt/4zreco/4zreco-maint fix-permissions --config /opt/4zreco/config.json
```

正常权限：目录 0750、文件 0644（目录本身在任务目录下，不对外暴露）。
