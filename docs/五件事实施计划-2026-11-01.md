## 批1 · B10 压缩器独立 profile

### 现状
`agentsForTask`（`server/task_llm.go:711`）：`agent.NewCompactor(plannerRuntime, "task-router")` —
压缩器与 planner 同模型，跟随任务 LLM 链（故障转移、额度轮转）。冷节点 major/minor 压缩是一次性
**Complete 调用**（`agent/compaction.go`），对模型的选择与 planner 的长会话需求完全不同，却被迫共用。
用户压便宜的高速模型跑 planner 却被压缩任务烧高价额度的场景真实存在。

### 改法

1. `server/task_llm.go`
   - `taskLLMRuntime` 加字段 `pin int64`（0=不钉，走原链）。
   - `current()`（:119-156）入口加 pin 分支：
     ```go
     if r.pin > 0 {
         if prov, cfg, ok := r.s.providerForProfile(r.pin); ok {
             sel.provider, sel.retry = prov, cfg.Retry
             return sel, nil // 绑定语义：profileID 保持 0，额度错误不推进任务链
         }
         // pin 失效（配置被删/无 key）→ 落回原链继续跑
     }
     ```
   - `agentsForTask`：读 `s.m.pg.GetSetting("compactor_profile_id")` 建独立 runtime，
     `agent.NewCompactor(compactorRuntime, "task-router")`。runtime 结构体带
     `CompactionWindow/nonStreaming/maxTokens` 等方法（同 plannerRuntime 语义，实测以其为准）。
2. `server/server.go`
   - `settingsPayload()` 加 `"compactor_profile_id": <int64>`（0=跟随 planner，回显可见）。
   - `putSettings` 加 `CompactorProfile *int64 \`json:"compactor_profile_id"\``，
     `*v >= 0` 存 `SetSetting("compactor_profile_id", int)`（<=0 清空）。即时生效：读设置发生在
     agentsForTask **构建时**，故改值后需让后续任务生效 + 当前任务的 compactor 继续 —— 与
     `workers` 设置同语义（对之后启动的任务生效），注释写明。
3. 前端
   - `web/src/lib/types.ts` Settings 类型加 `compactor_profile_id?: number`。
   - `web/src/app/(main)/system/settings/page.tsx`：压缩设置卡片（现
     `compaction_max_tokens` 所在处，:66/:110 一带）加「压缩器模型」下拉：
     选项 = `跟随规划器（默认）` + profiles 列表（`api.listLLMProfiles()`，llm 页已有同款取法）。

### 验证
`go build ./...`；手动说服力用例 = 设置 pin → 新任务跑一轮看 llm_usage 里 `compactor/session`
行的 profile_name 变化（llm_record 开着时看 session id `exp%d-compactor`）。

## 批2 · B2 / B6 / B7（「判断有数据」补完）

### B2 exhausted 零写回复盘触发

现状：`server/engine.go:1264-1303` 结算块，exhausted（撞步数上限/超时）且 `wrote == (agent.WriteCounts{})`
（`agent` 包，字段 Facts/Assets/Findings，`.Total()==0` 判零）的方向是「烧了整轮 token 却没留下
任何事实」，planner 往往把它当普通 done 掉了——B1 落了 stop_reason 但复盘本身没人触发。

改法：
1. `server/manager.go` 仿 `NotifyCancelled`（:2075 一带）加
   `NotifyReview(intentID int64, detail string)` → `pendingTriggers` append
   `agent.TriggerEvent{Kind: "review", IntentID: intentID, Detail: detail}`。
2. `server/engine.go` 结算块 `case reason == harness.ReasonMaxTurns / ReasonTimeout` 之后、终态落库
   前（state 已确定处）判断：
   ```go
   if state == "exhausted" && wrote.Total() == 0 {
       // 采集该意图最近 ~3 条步骤摘要（worker 轨迹）；来源与截断方式见下
       t.NotifyReview(intent.ID, fmt.Sprintf("...跑空复盘指令 + 步骤摘要"))
   }
   ```
   步骤摘要采集：复用 worker 轨迹读取（`list_worker_traces` 同源 db 方法；找不到便宜的现成接口时
   用 activity 流里该 intent 的最近 worker 事件摘要替代——实现时二选一，注释注明）。
   **不走**引擎超时收尾路径（`engine_timeout.go` settling 分支）——那里缺上下文且已逾期。
3. `agent/planner.go` `renderTriggers`（:178-225）加 `case "review"`：
   事件文本= 意图 #id（摘要）+ Detail（步骤回顾 + 指令）；
   指令语气：「这轮几乎没写回（事实 0/资产 0）——请保留步骤血缘（derived_from 落一条 fact）再做判断」。
   **不改 planner 种子提示词**（避免 SeedPromptVersioned churn；触发指令内嵌事件文本）。

验证：单跑一个撞步数上限的模拟 worker 场景（growth harness 已有 exhausted 先例测试可借改造），
断言 planner 下一轮输入含 review 文本。

### B6 Guard 归因补样本

现状：`guard/guard.go` 只有计数（`attrib map[string]int`，postToolUse :171-186），planner 看到
blocked/error 计数却不知道**哪条命令被拦**； Exhausted 复盘时对不上号。

改法：
1. `guard/guard.go`
   - 加 `type AttribSample struct{ Tool, Command string; TS int64 }`，`attribSamples map[string][]AttribSample`，
     每类保留最近 3 条，command 截断 200 字节。
   - `AttributionStats() map[string]any`：`{"blocked": n, "error": n, "ok": n,
     "samples": {"blocked": [{tool,command}...], "error": [...]}}`。
   - `Attributions()`（map[string]int）**保留**不删（还有别处用：任务页直读归因计数）。
2. `server/task_llm.go:704/:730`：`pl.SetAttributions(t.Guard.Attributions)` 改传适配闭包
   `func() map[string]any { return t.Guard.AttributionStats() }`；`main.SetAttributions` 同步。
3. `agent/tools.go`：`ToolSet.attributions` 字段与 `SetAttributions` 签名 `map[string]int` →
   `map[string]any`；渲染处 `out["guard_attributions"]`（:603-607）不用大改（直接放 map）。
   planner 提示词不加长——数据自带形状，样本数组字段名自解释。

### B7 意图级 token 记账

现状：`llmrec/llmrec.go:90-110 parseSession` 把 `exp1-worker-i3` 的 `i3` 后缀直接丢弃 → llm_usage
只有 exp 粒度；态势给意图上色「哪个方向烧了多少钱」做不到。

改法：
1. `llmrec/llmrec.go`
   - `parseSession` 加第三返回值 `intentID int64`（后缀形如 `i<n>`，非该形则 0）；
     顺带兼容现存 `exp2-planner`（无后缀 → 0）。返回签名变化 → 调用点 :126/:248（第二处是
     Complete? 实测:170/:248 两处 recordUsage 调用与一处 parseSession 调用）同步改。
   - `recordUsage` 加 intentID 参数，传给 `db.InsertLLMUsage`。
2. `db/llm_usage.go`
   - `LLMUsage` 加 `IntentID int64`；
   - **`llm_usage` 不在 schema.sql，由 `llmUsageSchema` 常量管理**（:29-48）——新列
     `intent_id BIGINT` 写进常量（新库）+ `EnsureLLMUsageTable` 在建表后补
     `ALTER TABLE llm_usage ADD COLUMN IF NOT EXISTS intent_id BIGINT`（老库，PG14+ 写法；
     CI 用 PG16 无碍）。
   - `InsertLLMUsage` SQL 加列。
   - `ExplorationStore` 加 `TokenByIntent()`（`db/exploration.go` token 区,近 `TokenStatsByWorker`
     :1544）：
     ```sql
     SELECT intent_id, COUNT(*), SUM(input_tokens+cache_read+cache_write), SUM(output_tokens)
     FROM llm_usage WHERE exploration_id=$1 AND intent_id>0 GROUP BY intent_id
     ```
     返回 `[]IntentTokenUsage{IntentID, Calls, InputTokens, OutputTokens}`。
3. `agent/tools.go` `graphOverviewData`（:470-619）
   - `compactIntents`（:22-）加第四参数 `tokens map[int64]int64`（总 token，0 省略）；
     `open/running/recent_done` 三处调用处从 `t.ts.TokenByIntent()` 拉一次 map 传入。
   - 渲染字段名 `tokens`，意图卡片显示「≈✕K tok」。

- B6/B2：单测 guard 样本环形 + engine 待写回分支（构造 worker 响应阻断）。

### web mock 条件化（首屏减重 ~242KB）

现状：`web/src/lib/api.ts:7-8,128` 无条件 `import { mockHandle } from "@/lib/mock/handler"`，
连带 `mock/data.ts`（242KB，Vercel demo 数据）进主 bundle——生产（NEXT_PUBLIC_MOCK 未设）白白载入。

改法：`api.ts` 该处改动态 import：
```ts
if (MOCK) {
  const { mockHandle } = await import("@/lib/mock/handler");
  return mockHandle<T>(init?.method ?? "GET", path, init?.body ?? null);
}
```
`MOCK === false` 时 webpack DefinePlugin 替换 + DCE，chunk 走不到（不管 chunk 是否仍 emit），
首屏主包不再包含 data.ts。函数已是 async 语义（返回 Promise），不影响调用方。
验证:`cd web && npx tsc --noEmit` + `NEXT_EXPORT=1 npx next build` 比对 main chunk 尺寸。

### JWT query token 收敛（N1 欠账的一半）

现状：`server/auth.go:258-266 extractToken` 对任何路径都接受 `?token=` query —— token 进
访问日志/Referer 风险。当初是为了 SSE（浏览器 EventSource 无法带 header）。

改法：`?token=` 只对 URL 直连 SSE 端点放行（白名单前缀/精确匹配，反查 `server.go:680-1000` 注册）：
`/api/exploration/activity/stream`、`/api/logs/stream`、`/api/update/stream`、
`/api/side-questions/{requestID}/events`。其余路径不再从 query 取 token（仍支持 cookie/bearer
不受影响）。前端已走 cookie/sessionStorage 双路径，无回归面。
验证：手工 curl 无 token 401 + 带 token SSE 200。
