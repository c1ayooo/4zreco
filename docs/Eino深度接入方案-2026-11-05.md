# Eino 深度接入方案（内核 eino 化 + 固定流程框架化；双图架构不动）

> 2026-11-05（v3 定稿）。目标：agent 内核从 norma 迁到 cloudwego/eino（ADK Runner 路线），治理类**固定流程**（审批中断/恢复、guard 链、上下文压缩、延迟工具门控）声明为框架级构件而非自研 channel 阻塞。
> v3 变化：把「compaction」拆成两套互不相干的系统（上下文压缩在 norma，冷节点压缩在本项目，v2 混为一谈已改）；明确 eino 图不能承载双图的四条硬约束（§0.2）；新增 §9 代码核对表，逐条标注「代码实测 / 设计文档 / 未验证」。
> 更正记录：v1 的「约 25 个文件」「compose.Interrupt」「空轮次续跑挂 BeforeModelRewriteState」「工具 handler 签名不变」四处经源码核对不成立，v2 已改；v2 的「compaction 三机制（compaction.go）」经核对是两套系统混写，v3 已拆。
> 蓝图照抄 4zrec 已验证路径（`~/4zrec/docs/eino-migration.md` 决策记录 + `docs/审批eino-HITL改造方案.md` 四轮迭代实施记录，生产实测过 HITL 全链），按本项目现状裁剪。
> **围栏全线不做**：4zrec 资产围栏经生产验证为失败设计（其自身体检数据：92% 审批是围栏 ask、其中 58% 是解析失败噪声、85% 的拒绝是任务取消连坐、围栏等待最长 20.9h）——审批管道被它变成噪声管道。本项目 ask 仅来自规则与 LLM judge，量小且每条都有明确裁决依据。

## 0. 结论摘要

深度接入 = 两件独立但有序的事，**加上一条不可协商的架构红线**：

1. **P1 内核 eino 化**：模型栈、agent 循环、工具面、挂点全部迁到 eino ADK Runner（norma 退役）；
2. **固定流程框架化**：审批走 eino 官方 HITL（`tool.StatefulInterrupt` + PG CheckPointStore + `ResumeWithParams` 验签），审批记录改不可变三表 + HMAC 哈希链；
3. **双图与调度不进 eino**（红线，见 §0.1）：资产图 × 探索图的编排、planner/worker 的角色分工、意图队列与终态分流全部留在 engine 状态机。

**eino 边界原则（骨架用框架，器官用纯 Go）**：eino 只承担编排与中断恢复的骨架——agent 循环（模型→工具→事件流）、ToolsNode 工具调用、审批型 HITL 的中断-检查点-恢复（将来任何「等人工」型流程，包括若围栏回归，其 HITL 也走这层）。**领域逻辑一律不进 eino**：围栏的命令目标提取/词法解析、范围匹配、拦截规则引擎、judge 提示、蜜罐签名、压缩决策算法等保持普通 Go 包/纯函数——eino 只提供挂点（middleware），挂点内调用它们。判定逻辑因此可独立单测、可被 CLI 等其他调用方复用；两层的衔接接口只有一个：**判定函数返回 ask → 骨架 Interrupt**。

**为什么这套分层不会把渗透流程做死**：本项目「怎么打」由四样承载——planner 的意图生成与 todolist、frontier 意图队列的领取顺序、DB 驱动的工具面（含 skill 中途解锁）、steer 中途注入。这四样都不依赖内核框架。eino 的 ChatModelAgent 本身是 ReAct 循环（`chatmodel.go:421`：model→tool→model），不是 workflow 图；v0.9.21 支持每轮改写工具面（`BeforeModelRewriteState` 可改 `ToolInfos`/`DeferredToolInfos`，`handler.go:164-168`）与运行前改写工具配置（`BeforeAgent` 可改 Tools，`handler.go:95-98`）。固定的是治理，不是策略。

顺序：**P0 审计不可变先行**（不依赖 eino、独立有价值、两模式共用）→ P1 内核 → P2 HITL → P3 前端 → P4 删 norma 收尾。全程 `hitl_mode: channel|eino` 双轨开关灰度。

不做清单（当前范围）：资产围栏本体（fence manifest、GuardedFenceStore 提权闸门、围栏降噪）。注意这与「围栏的 HITL 可以用 eino」不矛盾——若围栏未来以新形态回归，按边界原则拆装：提取/匹配是纯 Go 包，挂进 guard 链；等人工的那一步走 eino HITL 骨架，复用 P2 全部基建。

### 0.1 架构红线（不可协商）

| # | 红线 | 判定方式 |
|---|---|---|
| R1 | **双图架构留在 engine**：资产图（assets / exploration_nodes）与探索图（exploration_nodes / edges）的定义、写入、覆盖归账全部在 `internal/db` 与 `internal/server`，不进 eino 状态 | `internal/db`、`internal/server/engine*.go` 依赖树不得出现 eino |
| R2 | **planner/worker 调度留在 engine 状态机**：意图生成、frontier 领取、终态分流、暂停/恢复/取消语义不变；eino 只承载「一次会话推理循环」 | 禁止用 eino `Graph`/`Workflow` 表达 planner→worker 关系 |
| R3 | **不用 eino 的 agent 间原语**做 planner-worker 协作：worker 间过程级信息交换仍走 DB trace 检索（`search_all_worker_traces` / `get_worker_trace`） | 不引入 transfer-tool / subagent 作为调度通道 |
| R4 | **判定逻辑不感知 eino**：guard / intercept / judge / 压缩决策 / 蜜罐签名等包只提供纯函数或普通接口 | CI 门禁脚本（§8.2） |

R1-R3 的理由是同一条：图编排是编译期结构，一旦把探索顺序写成 eino 图，worker 的自由度就从「模型决定下一步」退化为「沿边执行」。本项目 worker 的核心行为是「领一条意图，自由选工具，做完即停」（docs/02 §四～§五），这条必须保住。

### 0.2 双图为什么不进 eino（可行性结论与证据）

结论：eino 能承载「图上的执行单元」（一次意图执行 = 一次 ChatModelAgent run），不能承载「图本身」。把双图编成 eino 拓扑，四条硬约束逐条撞墙：

1. **图编译后不可改**：`compose/graph.go:159-160` 定义 `ErrGraphCompiled = errors.New("graph has been compiled, cannot be modified")`，`graph.go:167` 据此拦截后续 AddNode/AddEdge。而本项目的图是运行时长的——`AddNode`（db/exploration.go:208）、`AddIntent`（:273）、`Link`（:312）、`Anchor`（:303）全由 worker 跑到哪写到哪；要加节点就得重建整图，等于每次写回都重编译拓扑。
2. **生命周期与共享域不同**：资产图跨任务、跨进程共享（assets / companies / company_scope）；eino 的 run 状态是单次 Run 内的 gob 快照（ADK CheckPointStore），不可 SQL 查询、不可跨 run 共享、不可给前端渲染。要共享只能外挂存储，那存储还是 PG。
3. **并发写一致性**：多个 worker 同时写回同一张图，靠事务与状态 CAS 保证（`CompareAndSetIntentState` db/exploration.go:447、`ResetRunningIntents` :396、`ReopenIntent` :410）。eino 图是单 run 内顺序推进，多 run 之间的并发一致性不在它的职责范围。
4. **语义错位（最本质的一条）**：探索图的边是推理血缘（fact→yields、intent→yields fact、fact→proves goal），不是控制流。把血缘边当控制边，等于规定「某个 fact 之后必须走某条 intent」——这正是「渗透不是固定流程」被做死的形态。

理论上的中间形态是把 frontier 遍历做成一个四步 eino workflow（取候选→排序→派单→判定继续）。技术上成立，但现有 frontier 已在 engine 跑通（意图队列 + debounce + 心跳 + 终态分流），搬过去收益为零，且让「遍历规则」从 SQL 条件变成图结构，违反 R2。**不做。**

要实证的话两个实验就够（各 1 小时内）：① 编译后再 AddNode，确认返回 `ErrGraphCompiled`；② 取一个真实任务的 exploration_nodes 全量序列化，量 gob 体积与 `runner_checkpoints.payload` 的 bytea 上限对照。

## 1. 动机

- **norma 单点**（P4 已消除）：上游仓库曾删除，一度以 go.mod replace 指向个人 fork（bus-factor=1）；P4 起依赖全删、类型基座 fork 内置于 `internal/norma/`；eino 是 CloudWeGo 活跃社区项目。
- **框架级中断续跑**（用户核心诉求）：现状审批 = worker goroutine 阻塞在 channel 上（`HandleAsk` select，分钟级）；进程重启/任务暂停 → ctx 取消 → 记录落 denied，**重启后同一工具调用要重跑重审**。eino checkpoint 下审批等待天然 parked，decide 后从中断点精确续跑。
- **审批数据不可变**：现状 `intercept_pending` 是普通可 UPDATE 表（缺口见 §2.2），改成 append-only 三表 + 哈希链 + `/api/audit/verify`。
- **跨仓收敛**：4zrec 内核已 eino 化；对齐后两边内核级特性可互相移植（本项目现在搬不动任何碰内核的特性）。

## 2. 现状盘点（本项目，均经代码核对）

### 2.1 内核面（迁移工作量的主体）

- norma 引用 **108 处（非测试文件内的出现次数）/ 58 个非测试文件**（含测试文件共 104 个）。v1 写「约 25 个文件」只覆盖了 `internal/agent` 的一部分，按实测修正后工作量约 2 倍。
- 按子包分布：`llm` 54、`tool` 52、`transcript` 15、`harness` 14、`permission` 12、`agentcore` 11、`skill` 5、`hook` 3、`compaction` 2、`noaadapter` 1、`mcp` 1。
- 文件分布：`internal/agent` 28 个、`internal/server` 20 个，其余在 `llmpool`/`llmrec`/`mcphttp`/`traffic`/`sidequestion`/`guard`/`tarpit`。**server 装配面不是「顺带改」，它与 agent 包同量级。**
- 与 4zrec 迁移前同款硬骨头：**上下文压缩**（norma/compaction 的 Pre/Reactive/ContextView，见 §2.1.2）、**延迟工具+skill 解锁**（deferred.go）、transcript JSONL、provider 装饰（llmpool 轮询池/llmrec 录制同层）、**工具上下文桥接**（actool.ToolContext，见 §3.2）。

### 2.1.1 自由度在哪一层（决定这次迁移的边界）

| 层 | 承载什么 | 现状实现 | 迁移是否触碰 |
|---|---|---|---|
| 策略层 | 下一步打什么、派哪条意图 | planner prompt + todolist + 触发事件（`planner.go`） | 不碰 |
| 调度层 | 谁先跑、跑多久、何时收 | engine 状态机 + frontier 队列 + 墙钟预算（`engine*.go`） | 不碰（红线 R1-R2） |
| 工具面 | 能看见哪些工具、能调哪些 | DB 实时解析（`ToolAugment`/`ToolResolve`，assembly.go:34-57）+ skill 解锁（UnlockSet）+ MCP | **碰**（P1-4/P1-5） |
| 注入层 | 中途加指令、空转续跑、收尾 | `steerHooks`（PreToolUse/PostToolUse/Stop）+ idlestop | **碰**（P1-7） |
| 传输层 | 模型与工具的往返 | norma harness.Query + agentcore.Session | **碰**（P1 主体） |

结论：本次迁移动的是最后两层，前两层不动。任何方案如果把策略或调度折进 eino，就违反红线。

### 2.1.2 两套「压缩」必须分开看（v2 混为一谈）

| 系统 | 压什么 | 代码位置 | 归属 | 迁移处置 |
|---|---|---|---|---|
| **上下文压缩**（会话消息 → 摘要，防上下文溢出） | 模型请求的消息数组 | `norma/compaction`：`Compactor` 实现 harness 的 `Pre/Reactive/IsOverflow`（interface 在 norma/harness/query.go:133-143），可选 `ContextView`（:145-147，直接构造请求数组）；调用点是 query.go:407（每次请求前 Pre）、:423-425（溢出后 Reactive 一次）、:770-775（ContextView 投影） | **框架能力，随内核一起换** | 必须用 eino 挂点等价实现，见 §3 表与 P1-5 |
| **冷节点压缩**（cold-digest：把探索图里冷掉的节点块压成 digest 节点） | 探索图的数据行，不是消息 | `internal/agent/compaction.go`（817 行，maintain/minor/major 三模式）+ `coldgraph.go`（330 行纯算法）+ `db/digest.go`（253 行存储）+ `tools_digest.go` | **本项目领域逻辑，纯 Go** | **完全不进 eino**，只把内部的 LLM 调用走 provider 桥（§3.2 同一层）。它的块大小 6、预算 65536、N=20/M=8 阈值、60s 冷却、提交前存活复检都是领域参数，eino 不该知道 |

判据一句话：**压消息的是内核能力（要迁），压图节点的是领域逻辑（不迁）**。v2 写「compaction 三机制（compaction.go，含 413 反应式）」把两者混成一条，会导致把冷节点压缩排进 eino 迁移量，凭空多出一大块并不存在的工作。

### 2.3 与 4zrec 的关键差异

- **无资产围栏**：ask 只来自规则(action=ask)与 judge；量级小（4zrec 411 条审批里围栏占 92%，砍掉后剩余 8% 量级）且每条自带规则名/模型判定依据——P3 降噪从「生死攸关」降为「展示质量」。
- **kind 分类学仍要做**，目的不是还债，是拆 decided 维度与前端筛选。但现状命名是反的：`decision_source` 列存的是 **ask 来源**（rule/model/unknown，schema.sql:1143-1145），不是决定来源。迁移要把这一列改名为 `ask_source`，并同步三处消费者：
  - 枚举校验 `server/intercept.go:428-431`（现在只认 model/rule/unknown）；
  - 前端类型 `web/src/lib/types.ts:1473,1517` 与筛选 `approval-records.tsx:668,824`；
  - **reason 前缀兜底**：`approval-records.tsx:50-54` 与 mock handler:2449-2454 在 `decision_source` 为空时按 `rule_id` 与 `reason` 前缀 `[模型]` 反推来源。v1 说「reason 前缀路由问题不存在」不成立——前端存在兜底反推；schema.sql:1144 的历史回填也用同一前缀。改名后必须删掉这段兜底，否则新旧两套来源判定并存。

## 3. 目标架构

```
                         ┌────────────────────────────────────────────────┐
   guard ask ────────────► tool.StatefulInterrupt(ctx, info, state)        │
   （不再 channel 阻塞）    │ state = {pending_id, tool, input_digest,       │
                         │          裁决依据}（可序列化，进 checkpoint）    │
                         └───────────────┬────────────────────────────────┘
                                         │ AgentEvent.Action.Interrupted
                                         ▼
                          Runner 自动写 checkpoint（PG: runner_checkpoints）
                                         │
                          hitl_pending_checkpoint 记录
                          (pending_id → checkpoint_id + interrupt_id)
                                         │
        ┌────────────────────────────────┼────────────────────────┐
        ▼                                ▼                        ▼
  审批中心卡片                     reaper 超时兜底              任务暂停 = park
  （轮询 intercept_pending）      （到点 INSERT timeout 决定）  （不再 cancel 等待中的 run）
        │ decide（全局凭据，带 decided_by）
        ▼
  INSERT intercept_decisions（append-only + HMAC 哈希链）
        │ 校验通过
        ▼
  runner.ResumeWithParams(checkpoint_id, &adk.ResumeParams{
      Targets: map[string]any{interruptID: {allowed, decision_row_id, sig}}})
        │ 工具包装在中断点 tool.GetResumeContext[*hitlState](ctx) 取回决定，
        │ 验签（decision_row_id + HMAC 与库中决定行核对）
        ├── allowed → 继续执行工具 → 结果 append 到 intercept_executions
        └── denied  → systemBlockMessage 作为 tool_result 回给模型，run 继续
```

**中断原语用 `tool.StatefulInterrupt`，不是 `compose.Interrupt`**（v1 写法不成立）：中断发生在工具调用内部，由 `WrapInvokableToolCall` 发出；`compose.Interrupt` 面向图节点，4zrec 全仓出现 0 次，其正确用法是 `tool.StatefulInterrupt(ctx, info, state)`（`askernel/middleware.go:409`）配 `tool.GetResumeContext[T](ctx)`（`askernel/middleware.go:342`）。state 只允许 gob 可序列化字段，且不放工具入参明文（体积与敏感度都不可控）。

固定流程框架化清单（哪些自研构件变成 eino 一等公民）。**每行都遵守边界原则：eino 列只写编排/挂点，逻辑本体（→右侧）仍是普通 Go 包**：

| 现状（norma/自研） | eino 落点（仅骨架/挂点） | 逻辑本体（纯 Go，不感知 eino） |
|---|---|---|
| guard 链（egress→tarpit→规则→judge）挂在 PreToolUse | `WrapInvokableToolCall` 内按序调用；ask → `tool.StatefulInterrupt` | guard/intercept 包的判定函数照旧 |
| HandleAsk channel 阻塞 + timer | Interrupt + checkpoint + reaper | 落库段（INSERT pending/卡片）照旧 |
| 工具调用循环（writeTool/readTool 注册面） | ToolsNode 编排 + `WrapInvokableToolCall` 内按 `IsConcurrencySafe` 读写分流（§3.3） | 工具 handler 经桥接层调用（§3.2） |
| 空轮次提醒 / 续跑指令注入（continuation/idlestop） | **不进内核**：ReAct 在「无 tool_call」即终态，中间件无续跑挂点；上移到 engine 再唤醒（§3.1） | 判定/文案函数 |
| 上下文压缩（norma/compaction：Pre / Reactive / ContextView） | `BeforeModelRewriteState` 做预算检查与消息投影（等价 Pre + ContextView）+ `WrapModel` 捕溢出错误触发一次 Reactive（4zrec V6 定案：不用 eino summarization） | 阈值/分块算法纯函数（从 norma/compaction 移植，不改判据） |

### 3.1 空轮次续跑：内核里没有这个挂点（v1 挂错了）

现状机制：模型只输出思考、没有正文也没有工具调用的回合，norma 视为自然结束；`steerHooks.Stop` 检测到 thinking-only 回合时注入一条续跑指令（带着已有思考继续），上限 `defaultEmptyTurnNudges=2`，额度按**每条意图总量**计（idlestop.go 头注释 + server/engine.go:531-620）。

norma 能做到是因为 `HookRunner.Stop` 的签名带 `prevent bool`（`harness/query.go:175`），可以拦住终态并塞一条消息让循环继续。eino 的 ReAct 循环在「模型无 tool_call」就是终态，`AfterAgent` 只在成功终态后被调用（`handler.go:144-158`），全仓没有 Continue 语义。**挂到 `BeforeModelRewriteState` 是无效挂点——那一轮模型调用根本不会发生。**

两条落地路线，先做 A，保留 B 作退路：

- **A（推荐）续跑上移 engine**：Run 正常结束 → 若终态为 completed、末条 assistant 消息无文本无工具调用、且计数未达上限 → 把续跑指令 append 进 transcript → 重新开一次 Run（同一 checkpoint 链、同一 runner 指纹）。语义与现状等价，代价是多一次建 runner 的开销。
- **B（退路）dummy 工具承接**：注册 `continue_turn` 工具，中间件在 thinking-only 回合把「结束」改写成对该工具的一次调用，循环内自然继续。缺点是 transcript 出现虚假工具调用，回放与前端展示要过滤。

### 3.2 工具桥接层（v1 说「签名不变」不成立）

`actool.ToolContext` 携带 8 个字段（`norma/tool/tool.go:22-50`），eino 的 `adk.ToolContext` 只有 Name 与 CallID（`handler.go:45-48`）。CoreTool 不能改个类型就进 ToolsNode，必须先有桥接层：

| actool.ToolContext | eino 侧来源 | 落地 |
|---|---|---|
| WorkingDir | 无 | run 级 ctx value（装配参数） |
| AgentID | 无 | run 级 ctx value |
| ToolUseID | `adk.ToolContext.CallID` | 中间件填入 |
| MaxOutputChars | 无 | 自建（capOutput 纯 Go，等价 norma/harness 的 capOutput） |
| OutputDir | 无 | 自建（超限落盘 + 首尾截断） |
| Emit(ProgressInfo) | eino 工具事件 / 自建 | 事件流桥接 |
| Tasks(*Manager) | 无 | 进程内后台任务管理器照旧 |
| Env | 无 | Bash 工具自建，不进内核 |

规模：`actool.CoreTool` 175 处引用、`actool.Errorf` 184 处。桥接层做两件事——`CoreTool → adk tool` 的适配器（一个泛型构造函数），与 `ctx → actool.ToolContext` 的模板注入（每次调用填 ToolUseID）。4zrec 有同款已验证配方（`askernel/session.go:38,134` 的 tcTpl + `middleware.go:423` 的 `tools.WithToolContext`），照它做。**这是 P1 的真实工作量主体，v1 漏了。**

### 3.3 并发语义映射（readTool/writeTool → 安全/独占）

现状：`readTool` 设 `ReadOnly=true, Concurrent=true`（tools.go:399-403），`writeTool` 不设；harness 依此让只读工具并行、写工具互斥。eino ToolsNode 默认并行且没有等价标记，必须显式落规则：

```
WrapInvokableToolCall 内：
  1. safe := 工具注册时的 ConcurrencySafe 标记（readTool→true，writeTool→false）
  2. safe == true  → 进入共享信号量（上限 MaxConcurrency），与其他 safe 工具并行
  3. safe == false → 按工具名互斥 + 全局独占（FIFO 等待所有在跑工具结束）
```

反例（禁止）：全局 mutex 一刀切。那会把并行只读探测串行化，worker 单轮耗时翻倍，而 worker 的墙钟预算是固定的，直接等价于探测能力下降。4zrec 的写法可直接引用（`askernel/middleware.go:418-424`：`safe := t.IsConcurrencySafe(input)` + `sched.acquire(safe)`）。

## 4. 分期计划

### P0 — 审批记录不可变（先行，独立价值，不依赖 eino）

1. **三表拆分，pending 冻结为只 INSERT**：`intercept_decisions(pending_id FK, decision, decided_by, decide_source web|im|auto|reaper, decided_at, seq, prev_hash, row_hash)`、`intercept_executions(pending_id, execution_status, output, ended_at, tool_use_id)`；展示侧视图 `v_intercept = pending ⨝ last decision ⨝ last execution`，server 查询改读视图，前端无感。
2. **不可变用「不做冗余列 + 触发器」实现，不要让两件事互相打架**（v1 此处自相矛盾：既要求三表 `BEFORE UPDATE OR DELETE` 一律拒绝，又要求 pending.status 由触发器随 decision 同步——同步动作本身是 UPDATE，会被守卫触发器拒掉）。定案：
   - `intercept_pending` 不再保留 `status`/`decided_at`/`audit` 这些会被改的列，`status` 改由视图计算（`pending` / 最后一条 decision 的 decision）；
   - 三表统一 `BEFORE UPDATE OR DELETE` 拒绝（迁移与归档用专用角色 `audit_writer`，触发器按 `current_setting('app.role')='audit_writer'` 放行，该 GUC 只由迁移脚本设置）；
   - 执行结果也走 append：`intercept_executions` 每次结果一条新行，视图取最后一条，等价现在 `CompleteIntercept` 的语义。
3. **HMAC-SHA256 哈希链 + 串行化 + 恢复锚点**（v1 只写了算哈希，没写并发与补插，落不了地）：
   - 链头表 `audit_chain_head(chain_id PK, last_seq BIGINT, last_hash TEXT)`；写决定行前 `SELECT ... FOR UPDATE` 该行（或 `pg_advisory_xact_lock(hashtext('intercept_chain'))`），保证两条并发 decide 不分叉；
   - `row_hash = HMAC(audit_key, canonical(seq, prev_hash, 行字段))`，`seq` 单调、写进行内；
   - 归档恢复补插旧行时**不接链尾**：插入到 `chain_anchor` 锚行之前（锚行记 `after_seq` 与 `baseline_digest`），`/api/audit/verify` 的返回要区分「历史区未纳入逐行校验」与「断链@seq」；
   - audit_key 从服务端密钥派生（与 jwt.key 分离）。
4. **消灭改写/删除路径**：删死代码 `DecideInterceptPending`；归档不再 DELETE（导出快照照旧、库内行保留）；恢复只重插缺失 pending 行 + 补插 timeout 决定行；conversations 级联改 `ON DELETE SET NULL`（drop/rebuild constraint）。
5. **decided_by**：鉴权中间件注入凭据身份（JWT 管理员/API key 名）落决定行。
6. **kind 分类学**：请求表加 `kind ∈ {rule, judge}`（枚举位预留，不建 fence 类）；`ask_source`（rule/judge，由现 `decision_source` 改名而来）与新的 `decision_source`（human/auto_cancel/timeout）拆为正交维度；同步改枚举校验、前端类型与筛选、删 reason 前缀兜底（清单见 §2.3）。

验收：psql 手工 UPDATE/DELETE 被拒；两条并发 decide 后链不断、seq 无空洞；手工改行后 `/api/audit/verify` 报断链并给 seq；归档恢复后历史行可展示且不污染链校验；全量测试绿。

### P1 — 内核 eino 化（feat/eino 分支，工作量主体）

1. **依赖**：`cloudwego/eino v0.9.21 + eino-ext model/claude v0.1.26 + model/openai v0.1.13 + eino-contrib/jsonschema v1.0.3`（4zrec 现网版本，V9 尖刺已验证依赖树无冲突；版本漂移则重跑尖刺）。

3. **provider 适配**：llmpool 轮询/健康熔断、llmrec 录制改为模型装饰器；usage 映射（`PromptTokens = input+cache_read+cache_write`，CachedTokens/CacheWriteTokens 分列）。

| norma 终态 | eino 侧来源 |
|---|---|

| ReasonMaxTurns | `ErrExceedMaxIterations` |

7. **续跑与收尾上移**（§3.1 路线 A）：engine 新增「终态后判定 → 注入指令 → 重开 Run」，计数落 DB（每条意图总量，等价 `defaultEmptyTurnNudges=2`）；auto_finish / PromptByReason 收尾走同一机制。

9. **行为基线**：engine 状态机不变；spike/ 目录验证（可引用 4zrec V1-V4/V9 结论，仅重验版本差异项）。

验收：分支上全量 `go test -p 1`（真 PG）绿；三个真实任务形态（planner 轮次、worker 工具循环、chat 多轮）行为与 norma 版一致；**逐项对照 norma harness 的既有行为清单**（capOutput/超限落盘、非流式、rawinput、事件保真、contextview、scheduling、settlement、timeout_settle、todo_reminder、tool_use_signature）各有一条用例；transcript 回放旧会话正常；12 种终态的映射单测全绿。

### P2 — 审批走 eino 官方 HITL（核心增量）

1. **PG CheckPointStore + 映射表**（v1 缺映射表，kill -9 恢复用例做不出来）：
   - `runner_checkpoints(checkpoint_id PK, task_id, intent_id, kind, version, fingerprint, payload bytea, created_at, updated_at)` 实现 `adk.CheckPointStore`（Get/Set，Set 用 `INSERT ... ON CONFLICT DO UPDATE` 支持 re-interrupt 复写）与 `CheckPointDeleter`（任务终态清理）；
   - `hitl_pending_checkpoint(pending_id PK, checkpoint_id, interrupt_id, task_id, created_at)`：人工决定后据此精确 `ResumeWithParams`。进程重启后内存态全失，这张表是唯一的恢复钥匙；
   - `SetRunLocalValue` 携带类型用 `schema.RegisterName` 注册（gob）；payload bytea 上限兜底。
2. **HandleAsk 拆两段**：落库段原样（INSERT pending + 卡片 + 写 `hitl_pending_checkpoint`）；等待段改为 `return tool.StatefulInterrupt(ctx, info, state)`。`pendingManager`/channel 退役。
3. **恢复链路**：decide 写决定行成功 → 按 `hitl_pending_checkpoint` 取 checkpoint_id + interrupt_id → 用 P1-8 的确定性装配重建 runner（指纹校验通过）→ `ResumeWithParams`；中断点 `tool.GetResumeContext[*hitlState](ctx)` 取回，**核对 decision_row_id + HMAC 签名**才执行——伪造 resume 不可放行。同轮多工具中断由 CompositeInterrupt 聚合，Targets 逐个给决定（未命中的 re-interrupt，官方语义）。
4. **reaper**：超时从 goroutine timer 改扫描器（复用规则 TimeoutAction + 全局兜底）；到点仍 pending → INSERT timeout 决定 → Resume；同时清孤儿 pending（进程硬杀遗留）。
5. **暂停 = park**：engine.pause 对等待审批的 run 不再 cancel（interrupt 已 checkpoint）；判定点是「该 run 是否有 `hitl_pending_checkpoint` 行」；非审批暂停保持现状（`rt.cancel()`，engine.go:268）。
6. **崩溃回退**：checkpoint 版本不匹配 / 载荷损坏 / 超上限 / 指纹不匹配 → 回退现状语义（决定照常落库，运行侧按 denied 收尾，任务级重跑可能重审）。**这是劣化路径，不是无损回退**，验收与对外描述都按此写。
7. **开关**：`hitl_mode: channel | eino`（settings），默认 channel 灰度切；两模式共用 P0 决定表。

验收：审批等待中 `kill -9` 后端 → 重启 → decide allowed → 从 checkpoint 续跑该工具不重审；denied → 模型收管控文本 run 继续；指纹不匹配时走回退且界面显示「需重跑」；reaper 到点自动落 timeout 并恢复；同轮两工具同时 ask 的聚合分发用例过。

## 5. 关键取舍

| 决策 | 理由 |
|---|---|
| **双图与 planner/worker 调度不进 eino（红线 R1-R3）** | 图编排是编译期结构，探索顺序会被锁死；worker 的自由度来自 prompt、意图队列、工具面、steer，与内核框架无关 |
| **骨架/器官分层：eino 只做编排与中断恢复，领域逻辑保持纯 Go** | 判定逻辑（提取/匹配/规则引擎/judge）可独立单测、可被 CLI 等复用、可整包替换；eino 挂点里只留一行调用。将来围栏若回归，同一套拆法 |
| 完整内核迁移，而非「审批外包一层 eino」 | Interrupt 依赖 eino 运行时；只包一层等于双内核并存长期化，比迁移更贵 |
| 照抄 4zrec V5/V6 定案（deferred/compaction 自研中间件，不用 eino 官方件） | 官方 toolsearch 无硬门控、summarization 是破坏式。注意：v0.9.21 已有 `DeferredToolInfos` + `WithToolSearchTool`，能力本身存在，缺的是**硬门控**——理由写成「门控必须自建」，不是「做不到」 |
| 围栏全线不接 | 生产实证失败（噪声管道）；本项目 ask 量小且自带裁决依据 |
| 决定拆 append-only 新表而非给 Resolve 加权限 | CAS 防乱序不防事后改写；不可变必须落存储层 |
| checkpoint 不兼容即回退 channel 语义 | eino 升级可能改 gob 格式；审批操作不被运行时问题阻塞（代价是任务级重跑可能重审） |
| P0 先行 | 独立有价值（防篡改），且两模式共用，HITL 灰度期间不丢数据 |

## 6. 风险与回退

- **续跑语义变化**（§3.1）：从进程内 prevent 变为再开一次 Run，成本是多一次建 runner；风险是计数口径漂移导致空转打不住。对策：计数落 DB、按意图总量、单测覆盖三条路径（续跑一次 / 续跑到上限 / 正常结束）。
- **工具面指纹漂移**（P1-8）：skill 中途解锁或 MCP 重连会改变指纹，导致恢复被拒。对策：指纹只覆盖「工具名集合 + schema hash + 解锁集种子」，不覆盖 MCP 连接的临时状态；MCP 断连由工具级错误表达。
- **并发退化**（§3.3）：一刀切全局锁会把只读探测串行化。对策：读写分流 + 基准用例（同一轮 8 个只读工具的总耗时不得高于 norma 版的 1.2 倍）。
- **终态丢失**（P1-6）：12 种终态映射漏一种，engine 就会走错分支（重试当收尾、或收尾当重试）。对策：表驱动单测 + engine 分支覆盖率检查。
- **checkpoint 体积**：RunCtx 含工作集消息，依赖 compaction 边界；bytea 上限 + 超限回退；上线前真实长任务压测。
- **多工具并行中断聚合**：Targets 分发义务（官方文档明确）；P2 验收必测「同轮两个 ask」；踩坑短期退路 = 命中 ask 的轮次串行（对该 run 生效）。
- **灰度**：hitl_mode 双轨，出问题切回 channel（P0 决定表共用不丢数据）。
- **旧数据**：历史 pending 行不动，视图合并展示；哈希链从新行起算，历史行落在 anchor 之前，不参与逐行校验。
- **eino 版本升级**：锁定 v0.9.21；升级前跑 checkpoint 兼容性尖刺 + 终态映射回归。

## 8. 验收与门禁

### 8.1 分期验收（汇总）

- P0：不可变性可被 psql 直接证伪（UPDATE/DELETE 被拒）、并发决定不分叉、恢复不污染链校验。
- P1：12 种终态映射单测全绿；norma harness 行为清单逐条对应用例；并发基准不高于 1.2 倍；transcript 旧会话回放。
- P2：kill -9 续跑不重审；指纹不匹配走回退；同轮双 ask 聚合。
- P3：筛选、徽标、审计校验入口三处手测。

### 8.2 架构门禁（CI 脚本，新增）

`scripts/check-eino-boundary.sh`，在 CI 与 pre-push 运行，失败即阻断：

1. `internal/db`、`internal/server/engine*.go` 的依赖树不得出现 `github.com/cloudwego/eino`（红线 R1-R2）。
2. `internal/guard`、`internal/intercept`、`internal/vulnintel`、`internal/honeydetect` 不得 import eino；这些包的导出函数签名不得出现 `schema.Message` 等 eino 类型（红线 R4）。
3. 全仓禁止用 `compose.Graph`/`compose.Workflow` 表达 planner-worker 关系（红线 R2 的可执行形式，白名单为空）。
4. `go.mod` 的 eino 版本必须等于锁定版本，`go.sum` 校验通过。

### 8.3 文档与代码同步

本方案涉及的三处命名/结构变更（`ask_source` 改名、`v_intercept` 视图、`hitl_mode` 开关）落地时同步更新：`docs/04-审批与拦截.md`（改表结构与审批链路图）、`AGENTS.md`（把门禁脚本加进常用命令）；`docs/01-双图架构.md` 不改——双图与调度不进 eino，描述未受影响，这也是红线 R1 的验证方式之一。
