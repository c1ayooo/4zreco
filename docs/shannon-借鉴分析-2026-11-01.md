# Shannon(KeygraphHQ)借鉴分析 — 2026-11-01

> 研究对象：[KeygraphHQ/shannon](https://github.com/KeygraphHQ/shannon)（AGPL-3.0，约 5.3 万行 TS，50k stars）
> 本地源码：`D:\xiangmu\aiai\shannon`（已 clone，可直接 grep 原文）
> 方法：三个并行深读（prompts 全部 80 文件 / worker 编排 168 文件 / CLI+Docker+docs），关键引述已回查原文核实。

## 0. 一句话结论

Shannon 的竞争力不在"多 Agent"，而在**把安全方法论编译成了状态机**：每类漏洞一套扁平 schema（队列 JSON）、每个阶段一个状态跃迁、每个判断附一条可执行问句、每份产物只有一个结构化工具出口。它的 prompt 约 30–35% 是禁止项/误报清单，15% 是自检，20% 是输出 schema，真正"方法论"只占 25%——这个比例本身就是设计。

另外它的整体定位与 ARTEX 不同：**Shannon = 白盒（读源码）+ 单次扫描 + 无 UI 的本地 CLI**；**ARTEX = 黑盒为主 + 常驻平台 + 双图态势 + 真实 SRC 作业**。所以不能整体照搬，只提取机制。

## 1. 定位差异总览

| 维度 | Shannon | ARTEX | 结论 |
|---|---|---|---|
| 测试模式 | 白盒（源码 + 实况）、proof-by-exploitation | 黑盒为主（资产测绘+探测）、vulnintel 情报 | 各自场景不同；白盒侦察思路可作可选模式 |

## 2. 值得借鉴的机制（按主题，P0 最高）

### A. Prompt 方法论（P0，零依赖，收益最大）

**A1. vuln 分析 prompt 的 12 段骨架**（`apps/worker/prompts/vuln-*.txt`，每份 233–324 行，五类逐节对齐）：

```
role/objective（成功标准写成"产物形态"）→ critical 四条定式（含相位隔离）→
starting_context（单一事实源=上游 deliverable）→ system_architecture（我前后是谁）→
definitions（先定义"什么算漏洞"）→ data_format_specifications（输出 JSON 逐字段示例）→
methodology（每项带 If failed → classify → suggested attack）→
proof_obligation_criteria（证据门槛）→ false_positives_to_avoid（分类专属误报清单）→
confidence（"when uncertain, round down"）→ negative_results_documentation（安全路径也要记录）→
deliverable_tools + conclusion_trigger（唯一出口 + STOP）
```

**A2. slot 分类把"有没有注入"降维成可判定问题**（`vuln-injection.txt:143-145`）：`SQL-val/like/num/enum/ident | CMD-argument/part-of-string | FILE-path/include | TEMPLATE-expression | DESERIALIZE-object | PATH-component` + "防护-上下文匹配表"（val 用 bind，enum/ident 用白名单；**sanitize 之后又 concat 的按"未防护"处理**）。原文：

> "If concat occurred **after** sanitization, treat that sanitization as **non-effective** for this path."

**A3. 三态判定问句**（`exploit-injection.txt:234`）——被拦时用一句可执行问句区分误报与 blocked：

> "Is this preventing factor a security implementation designed to stop this attack, or an external operational constraint?"（安全机制=误报；外部约束=blocked）

**A4. L1–L4 证据阶梯**（`exploit-injection.txt:209-229`）：L1 注入点确认 / L2 结构可控 / L3 数据外带或接管 / L4 关键影响；**L3 才允许标 exploited 且 ≥low**，L1–L2 只能 blocked。量化下限：初始确认 ≥3 payload，疑似被拦 8–10 变体，单漏洞 >10–12 次工具调用必须升级脚本；`Bypass Exhaustion Protocol` 未穷尽前禁止分类。

**A5. 观察 vs 推断的句子级边界**（`shared/exploitation/_reporting-standards.txt:9`）：

> "Make claims only about what you directly observed. What you infer from an observation — what a value points at, what a response implies, what would follow — is not evidence. Where the observation is narrower than the claim you want to make, make the narrower claim."

**A6. 无后果即无评级 + 自指矛盾检测**（`shared/exploitation/_severity-reasoning.txt`）：

> "If nobody ends up holding anything they should not … then the finding has no consequence to rate, and there is no tier low enough to be correct."
> "**Your own rationale must not refute your finding.** If the sentence you wrote for severity_rationale contains the reason the attack does not matter… you have written the argument for closing the finding, not for rating it."

**A7. 对抗式复核的信息隔离**（`sast/capella/review.prompt.hbs`）：

> "Assume every finding is a false positive by default… Explicitly ignore the original finder's prose reasoning and justification, as they may be hallucinated."

**ARTEX 落点**：`agent/promptcatalog.go`（worker/reporter/goals 三份默认 prompt 均已 DB 可编辑）。建议把 A3/A4/A5/A6 的原文级写法注入 worker 与 reporter 的纪律段；把 A2 的 slot 表做进 worker 的"参数级探测"提示（黑盒场景可简化为"参数位置 vs 过滤强度"矩阵）。**不需要新依赖，一次 prompt 迭代即可发版。**

### B. 报告与证据叙事（P0，接续 v0.4.4 公文工作）

Shannon 的报告结构（`sample-reports/shannon-report-crapi.md`，934 行）：

- Executive Summary + **Summary by Vulnerability Type**（每类一段，"没找到的"也写原因：XSS "exploitation attempts were blocked by framework-level protections"）
- 按类分章的 **Exploitation Evidence**，每条漏洞统一结构：
  `Summary（Vulnerable location / Overview / Impact / Severity）→ Prerequisites → Exploitation Steps（编号 curl + 真实响应）→ Proof of Impact（编号证据）→ Notes（观察细节如 verify=False）`
- 报告只组装**已提交到 git** 的证据（`reporting.ts readCommittedFile`），空类渲染占位，防"漏类被当成干净"
- report-executive.txt 是**落库工具**不是写手：`set-report-meta` 一次 + `add_finding` 每条一次，Markdown 由渲染器生成——**没有自由散文可发挥**
- 标题规则："names the defect and where it lives, and **never a consequence**"；"only ever makes a title more precise, **never louder**"；禁止 hedge 词（Theoretical/Potential）
- "未发现"不做负数记录：`negative_results_documentation` 要求安全路径（已查过没问题的）也要记录，证明覆盖率、防重复测试

**ARTEX 落点**：`agent/promptcatalog.go` 的 `ReporterDefaultPrompt` 已有结构（概述/影响/复现/证据/PoC/根因/修复），差距在三处：
1. 缺 **Prerequisites**（利用前置条件：需要什么账号/配置/网络位置）——SRC 评审最看重
2. 缺 **Proof of Impact 编号清单**（"已实现什么"逐条对应证据）
3. 缺 **"未发现/已验证安全"章节**——目前报告只写确认的漏洞，没有"本类已测且安全"的覆盖声明
4. 可加"标题不写后果、不 hedge"的规则
并配合 `report/docx_build.go` 的 `writeMarkdownish`：新增 `### 前置条件` 等小节的识别，让 Word 里出成规范小标题。

### C. 结构化提交 + 校验回灌（P0–P1，工程回报率高）

Shannon 的硬护栏（比 prompt 措辞可靠一个数量级）：

- `add_exploit` 是 **判别联合** `exploited | blocked`，`Type.Union` 二次校验；`vulnerability_id` 必须命中本类队列，否则返回**合法 ID 列表**——"you either typo'd an ID or imagined one"
- 校验失败以 `retryable:true` 工具错误回灌，模型在同一会话里**局部纠错**，不整段重跑
- 未处理的队列 ID 渲染为 `## Unprocessed Vulnerabilities`——遗漏可见
- 强制证据清单：payload、DB 指纹、当前用户/schema、全表名、最敏感表前 5 行——少一项不算 exploited
- 误报**不许**走交付工具，只写私有文件 `*_false_positives.md`

**ARTEX 落点**：`report_finding` 工具（`agent/worker.go`）已有必填参数；可加：
1. `finding_severity` 与 `evidence` 的**组合校验**（critical/high 要求 evidence 里出现真实响应片段/HTTP 状态/命令输出——否则降级为 inferred 或打回重试）
2. 返回结构化错误 + 合法枚举（vulnclass 现有列表）以便模型自纠
3. 报告只引用该 finding 已绑定的流量证据（已有 traffic binding 机制，可在 reporter prompt 里强制"引用 binding_id 时核对存在性"）

### E. 认证与交战规则（P1，真实 SRC 的明确 gap）

`configs/config-schema.json`：

- `authentication.login_type ∈ form|sso|api|basic`；`credentials{username,password,totp_secret}`（Base32 校验）+ `credentials.email_login{address,password,totp_secret}`；`login_flow: string[]`（1–20 条，每条 ≤500）；`success_condition.type ∈ url_contains|element_present|url_equals_exactly|text_contains`
- 登录执行：`$username/$password/$totp` 在 prompt 中**字面替换**，TOTP 现算（`generate-totp.ts`）；前置 `validate-authentication` 用真实浏览器跑一遍，产出 `submit_auth_result{login_success, failure_point}`——**凭据错了在开扫前就知道**
- `rules.avoid[] / rules.focus[]`（各 ≤50 条，`type ∈ url_path|subdomain|domain|method|header|parameter|code_path`）；`rules_of_engagement` 自由文本 ≤1000 字注入每个 prompt；`report{min_severity,min_confidence,sarif}`
- 注意其局限：**只有 code_path 是技术强制**（转 permission deny 规则），其余类型仅渲染进提示词；**限速只是文字约定**，无代码节流

**ARTEX 落点**：任务创建/目标配置里补结构化认证块（表单登录/API token/Cookie/TOTP/自定义 header + 成功判定），并在 worker 启动前做一次**登录自检**（HTTP 探测或浏览器），失败即报"凭据不可用"而不是让 worker 盲探。这是让 ARTEX 真正能打"登录后漏洞"的关键一步。

### F. 成本与可观测性（P1–P2）

- Shannon 按 agent 记 `AgentMetrics{durationMs,inputTokens,outputTokens,cacheRead/WriteTokens,costUsd,numTurns,model}` → 汇总 `totalCostUsd` + `usageAccountingComplete`（记账不全时明确标记）
- 现状：**CLI 未展示成本**（现成缺口）
- **ARTEX 落点**：`llmrec` 已有 `llm_usage` 表（profile/worker/status/input/output tokens）——补模型单价表 → `cost_usd` 列/视图 → 任务详情页与全局用量页展示"本任务花费 + 按 agent 分布 + 记账是否完整"。这张表就是现成数据源，改动小。

### G. 沙箱与分发（P2，只记方向，不建议近期动）

- Shannon：每次扫描一个 ephemeral Docker；repo 只读挂载 + 4 个可写 overlay（`.shannon/deliverables`/`scratchpad`/playwright）；非 root（UID 重映射）；`--shm-size 2gb`；镜像带 `worker-protocol` 标签门禁；Temporal 控面、bind mount 日志作数据面
- 其隔离是**进程+文件系统级，不是网络级**（safety.md 只靠"别打生产"约束）
- ARTEX 单体 + hostd 形态不同，整体容器化的收益/成本需要单独评估；**若做**，至少补 Shannon 缺的：默认拒绝出口 + 目标白名单
- 分发：npx + Docker Hub 多架构 + cosign；ARTEX 已有 release + LAN 本地源 + 一键更新，等价能力已覆盖

## 3. 不建议照搬

1. **Temporal**：ARTEX 的 PG 状态机 + 意图 CAS 已够用，引入 Temporal 会带运维复杂度，收益不成比例。
2. **Temporal 之外的"CLI 手抄类型"**：Shannon 自己在 `scan/pipeline.ts` 注释承认类型会漂移——反面教材；Go 用同 module 共享类型即可。
3. **整份白盒假设**：它的 vuln/exploit prompt 大量假设"可读源码、可给 file:line"。ARTEX 黑盒场景只能借"slot/防护匹配"的思路，不能直接复用其源码定位指令。
4. **ephemeral 容器**：ARTEX 的 hostd/流量代理/MITM 已深度依赖主机网络栈，整体容器化是架构级改造，不应为一个特性顺手做。
5. **npx 式分发**：形态不同，无必要。

## 4. 建议执行路线（三批，均可独立发版）

**第一批（P0，纯 prompt + 报告结构，1 个版本）**
1. Reporter 报告模板升级：每条漏洞加 `前置条件`、`Proof of Impact` 编号清单；报告末尾加「已测且未发现」覆盖声明；标题规则（不写后果、不 hedge）。
2. worker/reporter prompt 注入：观察 vs 推断边界（A5 原文）、无后果即无评级 + 自指矛盾检测（A6）、三态判定问句（A3）。
3. `report_finding` 证据强度校验：高严重度需真实响应片段，否则打回重试。

**第二批（P1，工程增强，2–3 个版本）**
4. 认证配置 + 开扫前登录自检（E）。
5. 任务状态补 `partial_reasons[]` + 成本展示（D 的封闭降级码 + F）。
6. 前端/SSE 契约版本化 + 未知事件告警（D）。

**第三批（P2，视需要）**
7. 覆盖矩阵做成"可执行能力注册表"（class → agent → 检测用例 → 最近 benchmark 证据），而非 Shannon 那种会腐烂的手写表。
8. 内容寻址/血缘（`ArtifactRef`）用于双图节点输入追溯。
9. 沙箱方向评估（出口白名单优先于整体容器化）。
