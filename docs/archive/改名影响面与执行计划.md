## 4. 执行计划（5 批，按依赖顺序）

### 批 1：品牌与文档（低风险，可先发）
- 前端：`app-config`、侧栏、登录页、document title、favicon/logo、空态文案
- README 按新品牌重写（定位/能力/架构/安装/截图）
- docs 全文替换品牌名（保留历史 CHANGELOG 里的旧名并注明曾用名）
- **截图重做**：用当前真实界面截图，敏感处打码（目标域名/IP、身份证/手机号、任务名、令牌）
- 验证：`npm run build:static` + 页面目检

### 批 2：分发标识（影响外链，需停机窗口小）
- GitHub 仓库改名（旧链接自动 301 重定向，但 release 资产直链会变）
- `install.sh` 的 `REPO`/`INSTALL_DIR`/`SERVICE`/`RUN_USER`/`IMAGE`
- `selfupdate.Repo` 默认值（或安装时 ldflags 注入）
- CI（release.yml 的镜像名/资产名）、Dockerfile/docker-compose 服务名
- 验证：新装一台干净机器走完 `install.sh --with-tools`

### 批 3：代码标识（最大改动）
- `go.mod` module path 改 + 全仓 import 替换（177 文件；用 `gofmt -w` + 全量 `go build ./...` 兜底）
- 二进制名/构建脚本/安装脚本/服务模板/日志前缀
- `ZRECO_*` → `{EN}_*`，**同时保留旧变量名兼容读取一个版本**（避免升级后环境变量失效）
- 前端 API 常量、localStorage 键、页面标题
- 验证：`go test ./...`（本地起临时 PG）+ CI 绿 + `build:static`

### 批 4：部署迁移（Kali 实机）
- 数据目录：`/opt/4zreco` → `/opt/{en}`（保留软链或一次性 mv + 更新 systemd）
- 服务：停旧 `artex` → 启新 `{en}`（保留旧 unit 文件一个版本做回退）
- 旧版本升级路径：老 `install.sh` 装过的机器，新版 install.sh 要能识别旧目录并迁移
- 数据库：表名不动（无需迁移）；连接串/配置键沿用
- 验证：Kali 实机迁移后登录、任务列表、附件、导出 Word 全通

### 批 5：验证与回滚
- 全量：`go build ./...`、`go test`、`build:static`、`bash -n install.sh`
- GitHub：新仓库 CI 绿、release 资产名正确、旧链接 301 可用
- 回滚：每批独立 commit/tag；批 3/4 保留旧名软链与旧 service 文件
